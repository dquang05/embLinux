## What is GDB?

**GDB (GNU Debugger)** is the standard debugging tool on Linux. When a program crashes or exhibits unintended behavior, GDB allows developers to pause execution at any arbitrary point, inspect variable values, trace call stacks, and step through instructions line-by-line — replacing trial-and-error guesswork with deterministic diagnosis.

GDB operates primarily in two modes:

- **Live debugging** — Running the program directly inside GDB, setting breakpoints, and examining state dynamically.
- **Post-mortem analysis (Core Dump)** — Analyzing a recorded memory snapshot (`core` dump) generated by the Linux kernel after an unhandled crash signal.

This laboratory focuses on hands-on live debugging techniques.

## Essential GDB Commands Reference

### Launching and Execution

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `gdb ./program` | | Start GDB loaded with the target binary |
| `run` | `r` | Start program execution from the beginning |
| `run arg1 arg2` | `r arg1 arg2` | Run program with command-line arguments |
| `quit` | `q` | Exit the GDB environment |

### Breakpoints

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `break main` | `b main` | Set a breakpoint at the entry of `main()` |
| `break file.c:25` | `b file.c:25` | Set a breakpoint at line 25 of `file.c` |
| `break func_name` | `b func_name` | Set a breakpoint at the function entry |
| `info breakpoints` | `info b` | List all active breakpoints and hit counts |
| `delete N` | `d N` | Delete breakpoint number `N` |
| `condition N expr` | | Breakpoint `N` only stops when `expr` evaluates to true |

### Execution Control

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `continue` | `c` | Resume execution until the next breakpoint or signal |
| `next` | `n` | Step over next line (does not enter function calls) |
| `step` | `s` | Step into next line (enters function calls if symbols exist) |
| `finish` | `fin` | Execute until the current function finishes, then pause |

### Inspecting Call Stack

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `backtrace` | `bt` | Print the complete call stack (active function chain) |
| `backtrace 10` | `bt 10` | Print only the innermost 10 stack frames |
| `frame N` | `f N` | Switch context to stack frame number `N` |
| `info frame` | | Display detailed metadata of the current stack frame |

### Inspecting Variables & Memory

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `print var` | `p var` | Print the current value of variable `var` |
| `print *ptr` | `p *ptr` | Dereference and print the memory content at `ptr` |
| `print &var` | `p &var` | Print the memory address of `var` |
| `display var` | | Automatically print `var` after every `step` / `next` |
| `info locals` | | List all local variables in the current frame |
| `info args` | | List all input arguments of the current function |
| `x/10x addr` | | Examine 10 hexadecimal words starting at address `addr` |

### Source Code Inspection

| Command | Shorthand | Description |
|---------|-----------|-------------|
| `list` | `l` | Display 10 lines of source code surrounding current PC |
| `list func_name` | `l func_name` | Display the source code of specified function |
| `list N` | `l N` | Display source code surrounding line number `N` |

> **Pro Tip:** GDB remembers the last executed command. Pressing `Enter` repeats the previous command immediately. This is particularly convenient when stepping through code with `next` or `step`.

## Lab 1 — Null Pointer Dereference

### Learning Objectives

In this lab, you will learn how to:
- Interpret GDB's `SIGSEGV` crash notifications.
- Use `backtrace` to trace the sequence of function calls leading to the crash.
- Use `frame` to switch stack contexts and `print` to evaluate variable states.
- Understand the importance of defensive NULL pointer validation before dereferencing.

### Scenario

An IoT device management subsystem maintains connected sensors. The lookup function `find_device()` returns `NULL` when a requested device identifier does not exist. However, the caller fails to validate the returned pointer before accessing struct members.

### Buggy Code — `bai1_null_pointer.c`

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef struct {
    int   id;
    char  name[32];
    float voltage;
} Device;

Device *find_device(int id) {
    if (id <= 0 || id > 99) {
        return NULL;        // Not found or invalid ID -> return NULL
    }
    Device *d = malloc(sizeof(Device));
    d->id      = id;
    d->voltage = 3.3f;
    snprintf(d->name, sizeof(d->name), "Device_%02d", id);
    return d;
}

void print_device(Device *d) {
    // BUG: No check for d == NULL before accessing members!
    printf("ID      : %d\n",     d->id);      // CRASH if d is NULL
    printf("Name    : %s\n",     d->name);
    printf("Voltage : %.1f V\n", d->voltage);
}

int main() {
    printf("=== IoT Device Manager ===\n\n");

    Device *d1 = find_device(5);     // Valid ID -> returns valid pointer
    printf("--- Device 1 ---\n");
    print_device(d1);
    free(d1);

    Device *d2 = find_device(-1);   // Invalid ID -> returns NULL
    printf("\n--- Device 2 ---\n");
    print_device(d2);               // SEGFAULT occurs here!
    free(d2);

    return 0;
}
```

### Compilation and Direct Execution

```bash
gcc -g -O0 -o bai1_null_pointer bai1_null_pointer.c

# Direct execution outside GDB — crashes without actionable root-cause info
./bai1_null_pointer
```

```
=== IoT Device Manager ===

--- Device 1 ---
ID      : 5
Name    : Device_05
Voltage : 3.3 V

--- Device 2 ---
Segmentation fault
```

### Debugging Strategy

The program crashes with `Segmentation fault` without any diagnostics. Answer these three core questions sequentially:

1. **Where did it crash?** → Run the binary directly inside GDB; allow GDB to trap the crash signal and inspect `backtrace` to pinpoint the function and line number.
2. **Which variable is faulty?** → Switch to the crash frame (`frame N`) and `print` variables to uncover anomalous values (e.g., verifying if a pointer equals `0x0`).
3. **Why did the variable become NULL?** → Place a breakpoint prior to the crash, step line-by-line (`next`/`step`), and observe state transitions to find where the bad value originated.

> **Null Pointer Signature in GDB:** A prominent indicator in GDB is `param = 0x0` within the backtrace. Encountering address `0x0` immediately signals a NULL pointer dereference.

### Debugging with GDB — Method 1: Direct Execution

> Best for rapid identification of the crashing function and line.

```bash
gdb ./bai1_null_pointer
```

```
(gdb) run
```

GDB intercepts the signal and halts execution at the fault site:

```

ID      : 5
Name    : Device_05
Voltage : 3.3 V

--- Device 2 ---
```

**Dissecting the Crash Line:**

| Component | Meaning |
|-----------|---------|
| `SIGSEGV` | Signal type: memory access violation |
| `print_device` | Function active at the moment of failure |
| `d=0x0` | Argument `d` holds value `0x0` (**NULL pointer**) |

```
^   ^ Frame 0 = Function active at the crash point
^                ^ d=0x0 -> NULL is visible right in backtrace

#1  0x0000555555555335 in main () at bai1_null_pointer.c:43
^ Frame 1 = Caller frame -> main() invoked print_device()
```

**Interpreting the Backtrace:**

| Component | Meaning |
|-----------|---------|
| `#0`, `#1`, `#2`... | Stack frame numbering. **`#0` is the crash site**, increasing upwards |
| Function name + args | Which function was running and the arguments passed |
| `file.c:N` | File and source line mapping |
| Read bottom-up | Execution path: `main()` -> `print_device(d=0x0)` -> crash |

```
(gdb) print d

```

The calling variable `d2` belongs to `main()`, not `print_device()`. Switch frames to inspect the caller:

```

43          print_device(d2);           <-- Offending call site in main()

```

> **Interpreting GDB Print Output:**  
> `$2` = GDB value history index (increments with each print)  
> `(Device *)` = Type cast showing pointer to struct `Device`  
> `0x0` = Virtual address `0` (NULL address — invalid for user-space dereference)

```c
    printf("Name    : %s\n",     d->name);
```

## Lab 2 — Buffer Overflow & Stack Protection

### Learning Objectives

In this lab, you will learn how to:
- Recognize why a standalone `Segmentation fault` or `Aborted` message is insufficient to identify the overflow site.
- Understand how GCC Stack Canaries operate and how they protect stack integrity.
- Use GDB to identify the exact **function** and **line** responsible for stack corruption.
- Use `print sizeof()` and `print (int)strlen()` to compare allocated capacity versus payload length.
- Understand why unbounded functions like `strcpy` must be replaced by bounded alternatives like `strncpy`.

### Scenario

An embedded serial command parser receives ASCII commands. The command buffer allocated on the stack is 16 bytes. An unbounded `strcpy()` is invoked to copy incoming data into the stack buffer. An oversized payload overwrites adjacent memory on the stack frame.

### Buggy Code — `bai2_buffer_overflow.c`

```c
#include <stdio.h>
#include <string.h>

#define MAX_CMD 16   // Maximum 15 characters + 1 null terminator

void process_command(const char *raw_input) {
    char cmd[MAX_CMD];   // Stack-allocated buffer (16 bytes)

    // BUG: strcpy enforces no bounds check!
    // If raw_input > 15 chars -> overwrites adjacent stack frame memory
    strcpy(cmd, raw_input);

    printf("Command received: [%s]\n", cmd);

    if (strcmp(cmd, "REBOOT") == 0) {
        printf("-> Rebooting system...\n");
    } else if (strcmp(cmd, "STATUS") == 0) {
        printf("-> System Status: OK\n");
    } else {
        printf("-> Unknown Command\n");
    }
}

int main() {
    printf("=== Serial Command Handler ===\n\n");

    printf("[Command 1]\n");
    process_command("STATUS");         // 6 chars - fits safely

    printf("\n[Command 2]\n");
    process_command("REBOOT");         // 6 chars - fits safely

    printf("\n[Command 3 - OVERSIZED]\n");
    process_command("AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA");  // 40 chars -> CRASH
    return 0;
}
```

### Step 0 — Standalone Run: Crash Without Location

Compile and run natively:

```bash
gcc -g -O0 -o bai2_buffer_overflow bai2_buffer_overflow.c
./bai2_buffer_overflow
```

```

[Command 1]

-> System Status: OK

[Command 2]
Command received: [REBOOT]
-> Rebooting system...

[Command 3 - OVERSIZED]
```

The program printed the output of Command 3, and then abruptly halted with:

- `*** stack smashing detected ***` — GCC detected corrupted stack metadata.
- `Aborted` — The program was terminated immediately via `SIGABRT`.

At this stage, we know a stack smashing event occurred, but we cannot answer:
- Which line of code performed the invalid write?
- Which function triggered the error?
- What exact input triggered the corruption?

GDB provides the tooling needed to resolve these questions.

---

### Step 1 — Under the Hood: GCC Stack Canary Mechanics

The error message originates from the **GCC Stack Canary** protection mechanism (enabled by default on modern Linux distributions).

GCC automatically inserts a random canary word into the stack frame of functions containing local arrays, positioned between the local buffers and the saved control registers (saved RBP and return address). Before the function returns, GCC checks whether the canary value remains unaltered. If altered, GCC calls `__stack_chk_fail()`, raising `SIGABRT` to kill the process.

```
High Memory Addresses
┌─────────────────────────────────────────┐  
│  Return Address (8 bytes)               │  RBP + 8
│  (Next instruction address in main)     │
├─────────────────────────────────────────┤  
│  Saved RBP (8 bytes)                    │  RBP (pointed to by $rbp)
│  (Caller's base pointer)                │
├─────────────────────────────────────────┤  
│  CANARY (8 bytes)                       │  RBP - 8
│  (Random value checked prior to ret)    │
├─────────────────────────────────────────┤  
│  cmd[15] (1 byte)                       │
│  cmd[14] (1 byte)                       │
│  ...                                    │  16 bytes total capacity
│  cmd[1]  (1 byte)                       │
│  cmd[0]  (1 byte)                       │
└─────────────────────────────────────────┘  
Low Memory Addresses                         RSP ($rsp points here)
                                             RBP - 24
```

**Offset Calculations Relative to RBP (x86_64 ABI):**

| Region | Offset from RBP | Virtual Address | Size | GDB Inspection Command |
|--------|-----------------|-----------------|------|------------------------|
| Return Address | `+8` | `$rbp + 8` | 8 bytes | `print/x *(long*)($rbp + 8)` |
| Saved RBP | `0` | `$rbp` | 8 bytes | `print/x *(long*)$rbp` |
| Stack Canary | `-8` | `$rbp - 8` | 8 bytes | `print/x *(long*)($rbp - 8)` |
| `cmd[0..15]` | `-24` | `$rbp - 24` | 16 bytes | `print/x *(long*)($rbp - 24)` |

When `strcpy` writes 40 bytes into a 16-byte buffer, the overflow cascades upward in memory, overwriting the canary, saved RBP, and return address. When execution reaches the closing brace `}` of the function, the compiler's inserted integrity check notices that the canary has changed, prints `stack smashing detected`, and invokes `abort()`.

> **Why Canaries Matter:** Without stack canaries, the CPU executes `ret` using a corrupted return address, jumping to invalid addresses (`0x4141414141414141`) or attacker-controlled shellcode. Canaries guarantee early, safe termination.  
> **Key Timing Detail:** The canary is **NOT** evaluated during the memory write. Evaluation occurs strictly at function epilogue prior to `ret`. That explains why subsequent `printf` and `strcmp` statements ran successfully after `strcpy` had already corrupted the stack.

---

### Reading Stack Memory via `print/x *(long*)($rbp - offset)`

Understanding the command syntax:

```bash
(gdb) print/x *(long*)($rbp - 8)
```

| Component | Meaning |
|-----------|---------|
| `print` | Evaluate and display expression |
| `/x` | Format output in hexadecimal notation |
| `(long*)` | Cast address into an 8-byte pointer (`long*` on 64-bit Linux) |
| `$rbp` | Hardware register RBP (Base Pointer for current frame) |
| `$rbp - 8` | Calculated address 8 bytes below current RBP |
| `*` | Pointer dereference operator to fetch 8 bytes of raw data |

**The Role of Saved RBP:**
When `process_command()` is called from `main()`:
1. `main()` has its own RBP pointing to its stack frame.
2. Function prologue executes `push rbp`: storing `main`'s RBP on stack at `[RBP + 0]`.
3. `process_command()` establishes its new frame pointer (`mov rbp, rsp`).
4. At function epilogue, `pop rbp` restores the original RBP to return control cleanly to `main()`.

If an overflow corrupts saved RBP:
- GDB will display `called by frame at 0x4141414141414151` (unwinding failure).
- Normal stack restoration becomes impossible.

### Corrective Fix — `bai2_buffer_overflow_fixed.c`

Replace unbounded `strcpy` with bounded `strncpy` and enforce explicit null termination:

```c
void process_command(const char *raw_input) {
    char cmd[MAX_CMD];

    // FIX: strncpy limits the maximum number of copied bytes
    strncpy(cmd, raw_input, MAX_CMD - 1);
    cmd[MAX_CMD - 1] = '\0';   // Guarantees null termination

    if (strlen(raw_input) >= MAX_CMD) {
        printf("[WARNING] Command exceeds buffer (%zu chars). Truncating to %d chars.\n",
               strlen(raw_input), MAX_CMD - 1);
    }
    // ... remainder of function
}
```

## Lab 3 — Stack Overflow via Infinite Recursion

### Learning Objectives

In this lab, you will learn how to:
- Identify stack overflow crashes characterized by thousands of repeated frames in `backtrace`.
- Use `bt 10` to inspect stack frames without flooding terminal output.
- Use `frame` and `print` to evaluate arguments across recursive frames.
- Use `display` to track variable changes across consecutive steps.
- Set conditional breakpoints using `condition` to catch execution states when error conditions arise.

### Scenario

A recursive countdown function `countdown(n)` is intended to count down from `n` to `0`. When `n > 0`, it recurses with `countdown(n - 1)`. However, the base case fails to return when `n == 0`; instead, it recursively invokes `countdown(0)` indefinitely until the stack memory is completely exhausted.

### Buggy Code — `bai3_stack_overflow.c`

```c
#include <stdio.h>

// Countdown function from n to 0
// BUG: Defective base case when n <= 0!
int countdown(int n) {
    printf("countdown(%d)\n", n);

    if (n > 0) {
        return countdown(n - 1);   // Recursive call with n - 1
    }

    // BUG: When n == 0, recurses indefinitely instead of returning!
    return countdown(n);           // INFINITE RECURSION when n == 0!
}

int main() {
    printf("=== Countdown Demo ===\n\n");
    int result = countdown(5);
    printf("Done: %d\n", result);
    return 0;
}
```

### Direct Execution

```bash
gcc -g -O0 -o bai3_stack_overflow bai3_stack_overflow.c
./bai3_stack_overflow
```

```
=== Countdown Demo ===

countdown(5)
countdown(4)
countdown(3)
countdown(2)
countdown(1)
countdown(0)
countdown(0)
countdown(0)
...
Segmentation fault
```

The function executes normally from `countdown(5)` down to `countdown(0)`. Once `n == 0`, `if (n > 0)` evaluates to false, falling through to `return countdown(n)`. This allocates new stack frames repeatedly until the stack reaches its resource limit (`RLIMIT_STACK`, typically 8MB on Linux).

### Error Flow Summary

```
countdown(5)
  └── n > 0 -> countdown(4)
        └── n > 0 -> countdown(3)
              └── n > 0 -> countdown(2)
                    └── n > 0 -> countdown(1)
                          └── n > 0 -> countdown(0)
                                └── n == 0 (condition fails)
                                └── return countdown(0)   <-- Self-invocation!
                                      └── return countdown(0)
                                            └── ... STACK EXHAUSTION -> SIGSEGV
```

### Corrective Fix — `bai3_stack_overflow_fixed.c`

```c
#include <stdio.h>

// Countdown function from n to 0
// FIX: Explicit terminating base case when n <= 0
int countdown(int n) {
    printf("countdown(%d)\n", n);

    if (n <= 0) {
        return 0;              // Base case: Terminate recursion cleanly
    }

    return countdown(n - 1);
}

int main() {
    printf("=== Countdown Demo (fixed) ===\n\n");
    int result = countdown(5);
    printf("Done: %d\n", result);
    return 0;
}
```

## Crash Identification Summary Matrix

| GDB Symptom | Crash Category | Immediate Action |
|-------------|----------------|------------------|
| `SIGSEGV`, valid function name, argument `0x0` / NULL pointer dereference | **NULL Pointer Dereference** | Run `bt` -> `frame N` -> `print <pointer_var>` to trace initialization point. |
| `SIGABRT` or `SIGSEGV`, corrupted addresses (`0x4141...`), `stack smashing detected` | **Buffer Overflow** | Inspect `#7 __stack_chk_fail`, examine user frame `#8`, compare `sizeof(buf)` vs `strlen(input)`. |
| `SIGSEGV` during function entry, `backtrace` repeats same function thousands of times | **Stack Overflow (Recursion)** | Use `bt 10` -> `frame N` -> inspect recursive terminating conditions. |

```
Crash Intercepted by GDB
    │
    ├── Examine Backtrace (bt)
    │       │
    │       ├── Parameter is 0x0 / NULL     ──►  Null Pointer Dereference
    │       ├── Target address is 0x4141... ──►  Stack Buffer Overflow
    │       └── Same function loops 1000s   ──►  Unbounded Stack Recursion
    │
    └── Switch Context (frame N) + Print    ──►  Isolate Root-Cause Variable
```
