# Core Concepts: Signals

This chapter covers the fundamental concepts of Signals in Linux, detailing what they are, how they operate, their primary use cases, and why they are generally unsuited for Inter-Process Communication (IPC).

## 1. What is a Signal?
A signal is a rudimentary form of inter-process communication, essentially acting as a **software interrupt**. It is a notification sent to a process to inform it that a specific event has occurred. 
- **Origin:** Signals can be generated by the Kernel (e.g., hardware faults, memory segmentation violations, user keystrokes like `Ctrl-C`), or explicitly sent by another process for synchronization or job control.
- **State Lifecycle:** From the moment a signal is generated until it is handled by the process, it resides in a **pending** state.
- **Default Actions:** Upon receiving a signal, a process will execute a default action defined by the kernel. These actions typically include Terminate, Ignore, Dump Core (terminate and generate a core file), Stop, or Continue.
- **Custom Disposition:** Developers can alter how a process reacts to a signal by explicitly ignoring it (`SIG_IGN`), restoring the default behavior (`SIG_DFL`), or registering a custom function known as a **Signal Handler**. 
*Note: `SIGKILL` (force kill) and `SIGSTOP` (force pause) are absolute; they cannot be caught, blocked, or ignored by any process.*

## 2. How Signals Work
When a signal is delivered, it interrupts the normal flow of execution of the receiving process. 
- **Signal Masking (Blocking):** A process can maintain a "signal mask" containing a set of signals that are currently blocked. If a blocked signal is generated, it remains pending until the process unblocks it. 
- **Standard Signals (Not Queued):** Standard POSIX signals (1 to 31) do not queue. If a specific standard signal is generated multiple times while it is blocked, the kernel simply records that it is pending. Once unblocked, the signal handler is executed only **once**, regardless of how many times the signal was fired.
- **Realtime Signals (Queued):** To solve the queuing limitation, Linux supports Realtime Signals (32 to 63). These signals are queued, meaning every generated signal will be delivered. Furthermore, they can carry a small payload (an integer or a pointer) via `sigqueue()`.

## 3. Signal Handling and Safety
Handling signals asynchronously introduces complexity due to the abrupt interruption of the main execution thread.
- **Async-Signal-Safe Functions:** Because a handler can preempt the main program at any arbitrary instruction, it must strictly avoid using functions that modify global state, use internal locks, or are not reentrant (e.g., `printf()`, `malloc()`). Only POSIX-defined **async-signal-safe** functions can be safely invoked inside a handler.
- **Synchronous Signal Handling:** To avoid the complexities and race conditions of asynchronous handlers, Linux offers synchronous mechanisms. Using system calls like `signalfd()`, a process can block signals and instead read them from a file descriptor just like standard I/O data. This approach is highly preferred in modern event-driven architectures and I/O multiplexing (`epoll`).

## 4. Primary Use Cases
Signals are generally employed for system-level notifications and process control rather than data transfer. Common use cases include:
- **Job Control:** Pausing, resuming, or terminating processes (e.g., `SIGSTOP`, `SIGCONT`, `SIGTERM`).
- **Hardware/Software Exceptions:** Handling fatal errors like invalid memory access (`SIGSEGV`), division by zero (`SIGFPE`), or illegal instructions (`SIGILL`).
- **Event Notification:** Notifying a parent process that its child has terminated or stopped (`SIGCHLD`), or responding to user terminal interruptions (`SIGINT`).
- **Timers:** Triggering events after a specific time interval using `alarm()` or POSIX timers (`SIGALRM`).

## 5. Why Signals are Rarely Used for IPC
Although technically classified under IPC mechanisms, signals are rarely used to exchange data between processes due to several severe limitations:
1. **Extremely Low Bandwidth:** Standard signals carry absolutely no data other than the signal number itself. Even realtime signals can only carry a minimal payload (a single integer or pointer), making it impossible to stream or transfer meaningful data structures.
2. **Asynchronous Complexity (Race Conditions):** Writing robust, race-free signal handlers is notoriously difficult. The restriction to only use async-signal-safe functions severely limits what can be done in response to a signal.
3. **Loss of Information:** Because standard signals do not queue, rapid successive signals of the same type will be merged into one. This guarantees data loss if the receiving process cannot handle them fast enough.

For actual data exchange, developers rely on robust IPC mechanisms like Pipes, Sockets, Shared Memory, or Message Queues.
